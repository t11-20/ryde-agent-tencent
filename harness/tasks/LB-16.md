## Steps

- Title: **FairTrip**
- Case study line (first line of the presentation): **Ryde — Multi-Agent Autonomous Dispute Resolution System**
- Blurb (must stay under 10 words): **Three agents resolve ride disputes with transparent evidence.** (8 words)

2. `submission/description.md` with these headings, in order, matching the hackathon form:
- **Project overview** — target scenarios (route deviation and no-show charge disputes), users (riders, drivers, support operations), value proposition (fast, evidence-backed, policy-grounded, explained decisions).
- **Real-world scenario insights** — source of the pain points (the Ryde challenge statement in `harness/reference/requirements.md`: manual review of GPS, chat, payment records; 24–72 hour resolution; inconsistent rulings; churn), target audience, core problems solved. Attribute industry figures to the challenge statement; never present them as FairTrip measurements.
- **Comprehensive solution design** — business architecture (submit → gather evidence → advocate → adjudicate → recommend action → explain to both parties); technical architecture (three agents, tool protocol, evidence package, DEMONSTRATION POLICY, deterministic money, decisive-evidence guard, observable UI, evaluation runner); how prompts drive the AI generation (role prompts, tool-request protocol, citation rules, Judge remedy selection without money, untrusted-evidence rule, JSON-only replies and one repair attempt).
- **Business value** — measured prototype results copied from `submission/metrics/scorecard.md` (fixtures passed, exact money, citation validity, trace completeness, consistency, p50 and max latency); expected impact written as projected, not measured.
- **Limitations** — synthetic data, demonstration policy, in-memory runs, no authentication, model-assessed confidence, local demo.
Use only numbers that appear in the saved scorecard. If a metric is missing, write "not measured".

3. `submission/presentation-outline.md`: one line per slide, 8–10 slides: case-study title slide (exact line from step 1), problem, users, architecture diagram, agents and tools, live demo R1, live demo N2, safety (X1 incomplete, X2 injection ignored), measured results, CodeBuddy build approach and a practical lesson, limitations and next steps.
